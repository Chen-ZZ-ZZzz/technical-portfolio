# LSST/ZTF/ANTARES Alert Data Quality Pipeline

A data quality pipeline for LSST and ZTF alert data via the ALeRCE and ANTARES brokers, and a broker-neutral transient monitor.

## Environment

- Python 3.13, venv at `.venv`
- Activate: `source .venv/bin/activate`
- Package managed with `uv`; install: `uv pip install -e .`
- Dev deps (pytest, pytest-mock): `uv pip install pytest pytest-mock`
- **Dependency changes are the user's deliberate step** (2026-10-03): the user runs `uv add` / `uv sync`; Claude never adds, removes, syncs, locks or installs packages. If work needs a package, Claude names it and stops. Enforced in `.claude/settings.local.json`: deny rules on `uv add/remove/sync/lock/pip/tool`, `uvx` and every `pip` form; `env.UV_NO_SYNC=1` (`uv run` never syncs implicitly, which could install from the uv cache without the network); a sandbox `denyWrite` on `.venv` and `uv.lock`. Outside Claude Code the same variable is set the same way: every active and dormant unit carries `Environment=UV_NO_SYNC=1`, and the stay-inside hook inherits it from the settings `env`.
- Key deps: `alerce`, `antares-client`, `pandas`

## Structure

```
src/rubin_qa/
    config.py          — installation settings and shared values (see "What lives in config.py")
    retry_budget.py    — the retry loop both broker clients use (call), and its run-wide sleep budget
    client.py          — ALeRCE API wrapper (_api_call, fetch_candidates, fetch_object_data)
    antares_api.py     — ANTARES API wrapper (fetch_antares_candidates, fetch_antares_locus) + the ANTARES helpers the tools share
    validators.py      — validate_completeness, validate_antares
    classifier.py      — _version_score, _method_weight, classify_object, classify_antares; the annotated ANTARES tag sets
    reporting.py       — build_qa_row, run_pipeline, build_antares_qa_row, run_antares_pipeline
    profiler.py        — object_profile (diagnostic deep-dive, all three surveys) + its own CLI
    photometry.py      — broker-neutral fetch layer: PhotPoint / SurveyObject, ALeRCE listings + light curves (ZTF, LSST)
    sky_catalog.py     — Legacy Surveys DR10 tiles (cached in cache/), local host/star/AGN matching
    tns.py             — TNS lookups via ALeRCE's throttled TNS service (two-pair canary rule)
    transient_monitor.py — new-transient scan of a sky cone (own CLI: uv run python -m rubin_qa.transient_monitor)
    replay.py          — the monitor's replay of past dates
    __main__.py        — CLI entry point
pipeline.py            — thin shim: uv run pipeline.py [survey] [page_size | oid ...]
tests/                 — pytest, mock data only (no live API calls)
.claude/hooks/stay_inside.py — PreToolUse hook: Claude's file tools write only inside the project (see below)
systemd/               — example user units; setup notes in systemd/README.md
pyproject.toml         — build: hatchling, scripts: rubin-qa, rubin-qa-profile
```

### Documentation: one home per fact (user, 2026-10-04)

Each fact is stated in one place. Every other place points to it by name (a section, a file, a function) and does not restate it: two copies drift apart, as the ANTARES locus count did in five places.
- **README**: results, measurements, evidence and method, and the explanations a reader of the project needs. The public record.
- **`systemd/README.md`**: deploying and running the units.
- **CLAUDE.md**: the working rules and decisions, the do-not-fix notes, and the facts with no other home. For evidence and explanations it points to the README, `systemd/README.md` or the code.
- **Code comments and docstrings**: what the code does and why it does it there. A measured number or a result lives in its doc home, and the comment points to it.
- **Memory**: only what none of these record.

Before writing a fact, find where it already lives; change it there and point to it from elsewhere. **Constants' values** (user, 2026-10-04): the code is the source of truth, and a constant's own comment may state its value. The README quotes one in a single case, a **recorded result**: the outcome of a validation or a measurement that the code then implements (the status-tier thresholds, d_DLR ≤ 4, the search and association radii, the lookback, the measured seconds per object). Every recorded result is one row of `tests/test_readme_quotes.py` (a README pattern and the constant it must equal), so a new quote is a new row, and a quote without a row is a bug. **Operational settings** (the request timeout, retry attempts and backoff, the retry budget, the deadline's factor and floor) are never quoted: the README names the constant instead ("retry policy: see `RETRY_*` in config.py"). **A past run's value stays, dated** (user, 2026-10-04: "60 s during the campaign"). It is a different fact from the current setting: it records what those runs used, and it never changes. A pointer would rewrite history the day the setting changes, because the results would then seem to come from the current value. Having no current counterpart to drift from, it needs no guard row. Why guard at all: the README's sizing example said 283 and 850 min, right once and wrong for weeks after `SECONDS_PER_OBJECT` and `DEADLINE_SLACK` changed, and nobody noticed (found 2026-10-04). The same table guards `systemd/README.md`'s summary of the unit files (cadence, command, start timeouts, read from the files) and the README's antares-client version (against `uv.lock`).

**Unit states** (user, 2026-10-04): `active`, `dormant`, `frozen`, defined under the unit table in `systemd/README.md`. Every doc uses these words that way, and no other word for a state (not "retired", not "disabled"). The difference that matters for work: dormant code may change and must keep working (its tests stay in the suite, its `.example` follows every change to the active units); frozen code does not change at all.

### Tests (conventions)

- **Tests patch the source** (user): a name is patched where the code under test reads it, e.g. a module's own constant in that module (`classifier.MAJORITY_THRESHOLD`) and the retry sleep in the shared loop (`rubin_qa.retry_budget.time.sleep`). When a value or function moves, its patches move with it, so a test never patches a copy the code no longer reads.

### Runtime directories (gitignored; the user's rule, 2026-10-02)

- `cache/`: anything that can be fetched again. Deleting it only costs time. (DR10 tiles, atlas, bricks, maskbits; replay candidates, neighbours and light curves; the LSST box census rows and their checkpoint; the point-source S/N rows; the DES-SN5YR head file; matplotlib's font cache; Python bytecode for the units.)
- `state/`: anything that can't be recreated. Deleting it loses information. (The transient monitor's state per footprint, the point-source watch, the host tool's TNS sample and pending TNS lookups, the pre-fix TNS sample kept as evidence, the latency samples, the frozen SSO monitor's state.)
- `logs/`: run output. It can be deleted at any time. (Run logs, replay results, host-matching scores and reports, TNS check results — all regenerable from `cache/` + `state/`.)

New files go by this rule, and a writer into `cache/` or `state/` writes a temp file and renames it. **Paths resolve from the repo root, never the current directory** (user, 2026-10-02): every data path comes from `config.PROJECT_ROOT` (`RUBIN_QA_ROOT` overrides it), relative command-line paths go through `config.from_root`, and modules and tools build their subdirectories from `config.CACHE_DIR`, `STATE_DIR` and `LOGS_DIR`, never `PROJECT_ROOT / "cache"` by hand. Only the tools' `sys.path` bootstrap lines stay file-based (`Path(__file__).parents[1] / "src"`). Pinned by `tests/test_paths.py`. `reports/` holds report outputs.

**What lives in `config.py`** (user, 2026-10-04): two kinds of value — settings of the installation (what is watched, where files go, network timeouts) and values used by more than one module. Tuning that belongs to one module's logic (windows, thresholds, radii) stays in that module. Not a count of users today: a count is a snapshot, and would move a value out and back in as modules change. No second copy anywhere.

**This directory is the user's local workspace, not the repo** (user, 2026-10-03): the repo is a much cleaner, curated subset of it, with many files and directories excluded from the sync (`reports/` and `logs/` among them); the user copies the reports wanted there by hand. A file existing here says nothing about what the repo holds: docs cite as evidence only reports the repo keeps and describe other runs' findings without naming their files. A pointer into `logs/` is fine where it is plainly local, regenerable run output.

## QA pipeline

One pipeline (`reporting.py`) with two broker paths. They share the retry loop and its budget (`retry_budget.call`; each client's `_api_call` passes only its own exception policy), the run deadline (`deadline_for`, `SECONDS_PER_OBJECT`) and the validator and classifier modules; only the fetch layer differs (`client.py` for ALeRCE, `antares_api.py` for ANTARES).

**ALeRCE (ztf/lsst):** `fetch_candidates()` → `fetch_object_data()` → `validate_completeness()` → `classify_object()` → `build_qa_row()` → `run_pipeline()`

**ANTARES:** `fetch_antares_candidates()` → `fetch_antares_locus()` → `validate_antares()` → `classify_antares()` → `build_antares_qa_row()` → `run_antares_pipeline()`

The report columns, status tiers and thresholds, completeness and flag tokens, the ALeRCE consensus and the ANTARES tag scoring, and broker support: README "QA Report", "Classification" and "Broker / Survey Support". The ANTARES tag sets, annotated: `classifier.py` (`SCIENCE_TAGS`, `PIPELINE_TAGS`). Rules kept here:
- **Failure messaging:** operator-facing messages go to stderr with one of two prefixes from config.py — `WARN: ` (`WARN_PREFIX`) for degraded-but-recoverable conditions where the run continues (retry attempts, an empty candidate page), and `ERROR: ` (`ERROR_PREFIX`) for failures whose caller cannot proceed (failed candidate fetch, pipeline exception, no rows produced). Every ERROR path returns no data or exits 1. stdout carries only normal output (progress lines, QA table). A run that produces no rows writes no CSV and exits 1.
- **Do not rescale `_version_score`'s cap:** it would move ZTF's tuned weights; why LSST's 201 vs 202 cannot be told apart is in its docstring.

## Transient monitor (transient_monitor.py, rebuilt 2026-09-27)

Broker-neutral: brokers are data sources, the monitor decides on photometry. Design origin: `transient_monitor_idea.md`, superseded where below differs. The evidence behind these rules is in the README sections "Replay Box Census", "Host Matching Validation", "Replay Validation" and "Asteroid Probe".

- **No state is an error; `--init` is the first run** (user, 2026-10-02). A live scan without `state/transient_monitor_<footprint>.json` exits 1 with an `ERROR:` naming the path, before fetching anything. `--init` evaluates everything as usual and records it as already seen without reporting it (a summary by category; no TNS lookups, no point-source watch entries), then creates the watch file; it is refused when state exists and with `--replay`. A missing watch file when the footprint has state is a `WARN:` plus a report line, never an error. Why, and the accepted trade-off: README "Replay Validation", First live run.
- **Daily unit:** `systemd/lsst-transient-monitor.service.example` + `systemd/lsst-transient-monitor.timer`; setup, schedule, write paths, timeout and checks: `systemd/README.md`. Rules: `ExecStart` takes no arguments (the live footprint is the CLI default; never `--init`, never `--dry-run`). Unit files are copied into the user's `~/.config`, so they carry only comments that serve the copied unit; a timer holds no paths, so it has no `.example`, no comments and no time zone. The user's installed, tested units are the source of truth: the examples mirror them. Units are tested by the user's local install, never by pytest; `tests/test_readme_quotes.py` reads the unit files only to check what `systemd/README.md` says about them.
- **Identity = survey object** (`ztf:ZTF26…`, `lsst:<diaObjectId>`), never a broker ID: an ANTARES locus is a place and can hold ZTF18 + ZTF26 + an LSST object. The state (`state/transient_monitor_<footprint>.json`) is keyed on these.
- **Fetch layer** (`photometry.py`): `PhotPoint(survey, survey_object_id, mjd, band, flux, flux_err, detected, broker)`, flux in nJy (difference image). Upper limit: flux NaN, flux_err = limit/5. LSST forced photometry: detected=False. **One broker, ALeRCE, for the whole live path** (user, 2026-10-03: one broker, one adapter, one set of failure modes): each survey's cone listing (`discover_alerce(survey, …)`; ZTF via the legacy client, whose JSON is a page dict with `items`, LSST via the multisurvey client, a bare list) and one `query_lightcurve` per object worth it (`needs_photometry`). ANTARES remains only in the QA pipeline, the host tool's TNS sample, the asteroid probe and the frozen SSO monitor; `tests/test_live_without_antares.py` keeps it off the live path (its docstring says how; 4 injected ANTARES uses, 2 of them swallowed, were all caught). Replay D rerun after the switch: identical, every field.
- **A rejection label says why, not what the pipeline did** (user, 2026-10-03), so a skip for a bad reason cannot hide under a harmless label: a listed object not worth a call carries the criterion that skipped it (`photometry_skip_reason`); one worth the call that comes back without detections is `empty_light_curve`; an old ZTF ID is `preexisting_ztf_no_rise`, like `old_no_rise`, because the rise paths run first (pinned by `test_an_old_ztf_object_rising_fast_is_re_brightening_never_preexisting`).
- **Footprints are cones, everywhere** (ALeRCE only searches cones): `(ra, dec, radius)`, membership = angular separation ≤ radius, so no declination correction, no RA 0/360 wrap, and every margin is radius + 1°. Presets in `config.FOOTPRINTS`; **ecdfs is the live footprint** (decided 2026-10-02, `LIVE_FOOTPRINT`, the CLI default), D the COSMOS test replay, C the former live candidate. ANTARES's cone (tools only) is `antares_api.sky_distance_clause`. The DR10 brick list is a cone on brick centres too (user: one shape, so nothing can quietly keep using the other); the 0.1° catalogue tiles and DR10's bricks are how the catalogue is cut, not footprints. **Deliberate exceptions — do not "fix" them:** `tools/atlas_query_contract.py` fetches an RA/Dec superset box on purpose (an oracle has to be independent of the thing it checks); `host_match_check.random_positions`'s flat-sky step (its comment says when to make it exact): its bias on the chance-host rate is ≲0.1 pp against that rate's own 0.93 pp error. The 2026-10-01 census is box-based and kept as run.
- **new**, per survey on its own history: first detection within N=14 d, ≥ 3 detections over > 1 night, a quiet point within X=10 d before it with 5·flux_err < first-detection flux. LSST can never bracket its own onset (forced photometry starts at or after the first detection), so an LSST onset may be bracketed by a ZTF upper limit on an associated ZTF object (`bracketed_by_ztf`). **Depth is tested against the *first* detection — decided 2026-10-02, stays:** bracketing claims the object was not there at the brightness of its first detection; against the brightest-so-far (88% vs 45% of new ZTF objects bracketed) a shallow quiet point would pass and prove only a rise, which `rising` already covers.
- **Every path needs detections on more than one night** (`spans_nights`, ≥ `MIN_SPAN_DAYS` 0.5 d), checked first in `evaluate` (2026-10-01). Why and the cost: the `MIN_SPAN_DAYS` comment.
- **rising** (main LSST path): recent onset, same band, earliest vs latest post-onset flux (forced included) ≥ 3σ and ≥ 0.3 mag over ≥ 0.5 d. **rapid_rise**: ≥ 1 mag within 3 d, any age (old object → `re_brightening`). **On an old object the rise must persist** (user, 2026-10-03; `rapid_rise(persistent=not recent)`): the elevated level seen on two nights, phrased as persistence because a pair-span rule would let a single bad detection or a passing asteroid through. Why and the cost: the `rapid_rise` docstring; its effect on replay D: README "Replay Validation". New objects' `rising`/`rapid_rise` are unchanged. Tests: a spike on one night only is no alert, the same spike still up the next night is `re_brightening`; dropping persistence fails 4 tests, asking it of every object 18.
- **unbracketed**: parked, re-judged each run, expires when the first detection leaves the window.
- **One event, one alert** (2026-10-02): another survey's detection within `ASSOC_RADIUS_ARCSEC` (1.5″) of an object already reported becomes a *note* on that alert (`DayResult.notes`; replay records carry `note_on`). Candidates are taken in order of first detection, so the survey that saw the event first holds the alert; the note keeps its own category and path. Matched on positions kept in the state (`reported[key]` has `ra`/`dec`), so it holds on a day the first survey's listing failed. Same-survey neighbours are a recurrence (context lines), not grouped. The cases that prompted it: README "Replay Validation".
- **TNS in the live report** is display context, looked up after the verdicts (`_add_tns` → `tns.tns_lookup`, every object by position). Every alert carries a TNS line: the record (matched within 2″); `none yet; asked again each run for 30 d`; or `unavailable (lookup failed); asked again …`. **"none" is re-asked like "unavailable"** (user): it only means nobody had reported the object yet (SN 2026kfw's TNS report came 5 days after the replay alert). Both go into the state (`tns_watch`, positions kept) and are asked again every run for `TNS_RECHECK_DAYS` (30), one paced call each, no canary (only a record is news). A record that appears is printed under "TNS for earlier alerts" with its lag. Any exception in a lookup is caught: never fails the run. An older state is rewritten on read (`lsst_newest_mjd` → `newest_mjd` per survey; old ANTARES-locus `tns_pending` entries dropped).
- **Filters**: galactic plane, and LSST's own asteroid ID (`ssObjectId`). Nothing is filtered on the sky context; broker classifications and TNS are report-only. **Known gap since 2026-10-03:** ALeRCE's ZTF detections carry no `ssnamenr`, so ZTF has no asteroid ID; the two-night rule covers almost all of it, and what gets through surfaces as an alert a human can dismiss — **user, 2026-10-03: a low chance, left as it is for now.** Evidence: README "Asteroid Probe".
- **Decision table** (`SKY_CATEGORY`, user's design 2026-10-01): two separate axes. The **sky context** (DR10 verdict + AGN flag on the assigned source) alone decides the category: `host` (incl. `agn_host`, a context note), `agn` (`agn_nuclear` on a host or point source), `orphan`, `point_source`, `stellar`, `unchecked` (catalogue gap or unavailable). The **path** — `bracketed`, `rising`, `rapid_rise`, `re_brightening` — is the confidence label; a report reads `host · rising`. Names claim only the sky. No "dropped" cell; `sky_context` raises on a combination missing from the table. Re-reporting keys on the (category, path) pair (state field `pairs`). Tests enumerate all 5 path cases × 8 sky contexts. Why: README "Replay Validation", the decision table.
- **DR10 matching** (`sky_catalog.py`): tiles of 0.1°, fetched on demand from Astro Data Lab TAP and cached per catalogue version. Verdicts in order: `stellar` (Gaia parallax or PM ≥ 5σ within 1″) → `point_source` (nearest non-piece source within 1″ is a PSF) → `host` (directional light radius ≤ `HOST_DLR_MAX`, flagged `nuclear` within 1″ of the centre, 2″ for atlas hosts) → `none`. AGN is a flag on the assigned source, never a verdict, and "no measurement" is never "not AGN". Decided and measured, with the numbers in README "Host Matching Validation": `HOST_DLR_MAX` = 4 and `ATLAS_RADIUS` = `sma_moment`; `point_source` before `host`; **no S/N floor on the point-source rule** (user's decision, left as measured; SN 2026kfw stays `point_source`, a known limitation; a floor would be in S/N, never magnitude); no compact-host rule.
  - **Ellipse conventions — do not "fix" them from the docs:** major axis at 0.5·atan2(e2, e1) East of North; `shape_r` = half-light radius along the major axis. The DR10 catalogue page and the atlas table document the mirror image. Anchored in tests by fixtures read from the pixels (`tools/pa_from_pixels.py`); evidence in README.
  - **Pieces belong to their atlas galaxy in every rule:** any row inside an atlas ellipse (maskbit 12) other than the galaxy itself (`L3`/−1 pieces, and point sources fitted on top, such as NGC 873's nucleus) is excluded from the host search and the point-source rule, so a transient on a nucleus becomes host + `nuclear`. The atlas galaxy uses the atlas's own ellipse only where it was measured (`sma_moment > 0`).
  - **Host candidates in two steps:** Tractor extended sources within `SEARCH_RADIUS_ARCSEC` (30″), plus every atlas galaxy with separation < `HOST_DLR_MAX` × its major-axis radius. The atlas is fetched once per footprint (`footprint_atlas(cone)`, cone radius + `ATLAS_MARGIN_DEG`; why 1°: its comment) and loaded lazily by the monitor; if it fails, the run continues with step 1 and warns once.
  - **Cache keyed on catalogue versions** (`cache/ls_dr10+sga2020/…`, from `TABLE` and `ATLAS_TABLE`), so a new release refetches instead of mixing versions; a cached file missing a column is refetched too.
  - **Catalogue gaps:** where DR10's fitting gave up (BAILOUT) no sources exist, so empty sky there is not an orphan. `catalogue_gap` checks the maskbits of every brick overlapping step 1's 30″ search area (the area, not the point: a host centred in a gap is lost even when the SN is outside it) → `unavailable`, never `none`. The monitor loads the footprint's brick list with the atlas; without it every crossmatch says "catalogue gaps not checked". Step 2 is unaffected (`tools/atlas_query_contract.py`). Backfilling from DES DR2 only if the gap count proves large.
  - **Fetch failures never become data:** errors raise `CatalogError` and are never cached; an empty answer is returned but not cached; requests send an explicit `MAXREC` and a result at it is rejected as truncated; maskbits accept only a FITS body, 404 = no brick. Each failure path has an injected-failure test. **Cached files are checked on read** (2026-10-02): a damaged tile or maskbits file is warned about, deleted and fetched again (`DAMAGED_FILE_ERRORS`), never a crash; `tile_is_cached` reads the whole file (a truncated gzip keeps its header). The prefetches ask `maskbits_is_cached`, a header-only completeness test. All cache writes are temp file + rename. Measured by truncating cached files (gzip tiles cut anywhere raise; 344 maskbits cuts never read back wrong; 1,064 cuts swept for the completeness test) and audited (1,266 tiles, 514 maskbits, 0 damaged); confirmed live on damaged copies.
  - **`tests/fake_tap.py`** applies the q3c cone of the query it receives; its reading of q3c is checked against Data Lab by `tools/atlas_query_contract.py` (on demand, outside the suite; rerun if the footprint query changes).
- **Point-source watch** (`point_source_watch`, called by the daily report and every replay, user 2026-10-02): every `point_source` alert goes into `state/point_source_watch.json` (shared by all footprints and replays; not subject to the state's 60-day retention) and is looked up in TNS weekly per alert until classified, or until 180 d after the alert. Only spectroscopic supernovae count, judged on TNS's classification **type**, never the prefix (`SUPERNOVA_TYPES`; unclassified = AT with type `{id: None, name: None}`; AT 2018hyz, a TDE, comes back with prefix `TDE`). Any other class settles the alert and is said in the report, with a note for the nuclear types (`NUCLEAR_TYPES`). Distinct TNS names below S/N 7 (`PS_REVISIT_SNR`) are counted; `PS_PATTERN` = 3 is a pattern, then a NOTICE every run, asking to measure the floor again. Findings carry a fingerprint of the point-source rule, so changing the rule or `PS_PATTERN` is what stops the notice. One watch line per report; never fails the run; `--dry-run` writes nothing.
- **Replay** (`replay.py`, `--replay FIRST_DAY LAST_DAY`; the user's design, 2026-10-01). The LSST stream stopped 2026-07-14, so replay is the only way to exercise the LSST path. It filters only on what cannot change: candidates first detected in [first day − 14 d, last day], listed in ≤ 7-day chunks, cut to detections spanning > 1 night (lossless; an `n_det ≥ 3` cut would not be). The old `--as-of` filtered on summary fields read today and was removed. One cached light-curve fetch per candidate; every replay cache file is written temp + rename and checked on read (damaged → warned, deleted, refetched). Every DR10 tile and brick the crossmatch can need is prefetched before judging; each day is then judged by the live code (`judge_day`) on light curves sliced to that day, with no API calls; crossmatches that could not be made are counted, never passed as results. ZTF objects at an LSST candidate's position are association context only, never judged. `--estimate` prices without fetching; `--compare-cuts` is the equivalence test. **Cost gate** (2026-10-02): `replay.price()`; `--compare-cuts` prices both sides before either fetches; above `CONFIRM_THRESHOLD_SECONDS` a replay asks y/N on a terminal and refuses without one unless `-y/--yes` (a replay is never scheduled). Method, the discarded first run, results and the TNS check: README "Replay Validation".
- **The live monitor guards both listings** (`check_listing`; LSST 2026-10-02, ZTF 2026-10-03): ALeRCE's listing can fail silently (a heavy query sometimes answers 200 with zero items, sometimes 504, sometimes data after ~40 s), and with Rubin off sky an empty listing is the normal state for weeks, so it must not look like a failed one. An empty listing is checked against ALeRCE's newest object of that survey in the cone (`order_by=lastmjd` DESC, 1 row, `lastmjd` ≥ min(window start, stored newest − 1 d); the stored newest is `newest_mjd` in the state): older than the window → `quiet`, with the date of the last detection; inside the window → the listing failed; nothing or an error → unverified. Every failure prints `… listing (ALeRCE): FAILED - …` plus an `ERROR:` and exits 1, after the other survey is reported and the state saved (a missed listing loses nothing). No stored newest: the whole cone is asked once (~55 s on ecdfs for LSST, against the 60 s request timeout). The replay re-asks an empty chunk day by day. `total` in the response is not a count.
- **Replay footprint:** box D, replayed in March–May (census 2026-10-01, box-based, kept as run; `tools/lsst_box_census.py`); RA 240–255, Dec −25..−15 rejected. Why: README "Replay Box Census".

## Known API quirks

The ALeRCE and ANTARES quirks, the three ceilings on a stalled broker (request timeout, retry budget, run deadline) and how `SECONDS_PER_OBJECT` was settled: README "Known API Quirks" and "Broker Latency Sampling Campaign"; the reasoning behind each constant, and why `DEFAULT_SECONDS_PER_OBJECT` is unreachable today: its comment in `config.py`. ALeRCE's TNS service quota and the two-pair canary rule: README "Replay Validation" (the oracle) and `tns.py`. The profiler: README "Diagnostic profiler". Kept here, with no other home:
- **ANTARES code lives once** (2026-10-03): the helpers the repo still needs — `antares_errors()`, `is_solar_system`, `locus_survey_ids`, `sky_distance_clause` — live in `antares_api.py` and are imported by the tools; `tests/test_antares.py` fails if a tool re-implements one. **Deliberate exception — do not "fix" it:** the frozen SSO monitor (`antares_sso_monitor.py`) keeps its own self-built ANTARES code. It is an artifact (user, 2026-10-03): not in use, no plan to reuse it; a future SSO monitor would probably be built on the Fink broker, as new work. A frozen copy cannot drift, and `tests/test_sso_frozen.py` makes that true by construction: it pins the SHA-256 of the monitor's files (the script, its service example and its timer, renamed from `.timer.example` by the user 2026-10-04) and of the one function it imports (`config.now_mjd`), and that the script imports nothing else from the package. Recording a new hash there is the deliberate unlock.
- ANTARES `ant_survey` codes in the light curve and alerts: **1 = ZTF detection, 2 = ZTF upper limit, 4 = LSST detection** (verified 2026-09-27; 2 is *not* LSST). LSST detections carry `ant_mag` plus ~140 `lsst_diaSource_*` / `lsst_diaObject_*` fields, incl. `lsst_diaSource_ssObjectId` (Rubin's own SSO association, 0 = none), `_reliability`, `_snr`.
- ANTARES: LSST alerts attach to existing loci within ~1″, so most LSST detections sit on **old ZTF loci** (`ANT2018…`–`ANT2021…`). A query on `properties.oldest_alert_observation_time` never selects them; the `properties.survey.lsst.dia_object_id` array is not usable in an ES `exists` filter; the Rubin tags (`young_rubin_transients`, `lsst_scimma_quality_transient`) are the working server-side handle.
- ANTARES `locus.tags` returns plain strings (not objects); `locus.properties` holds `num_mag_values`, the quality-filtered detection count.
- LSST forced photometry (ALeRCE `query_forced_photometry` / `query_lightcurve`) **starts at or after the first detection** (16 of 16 objects checked 2026-09-27; several stop at exactly 10 epochs), and ANTARES serves no LSST forced photometry or non-detections at all, so no broker provides pre-onset LSST photometry.
