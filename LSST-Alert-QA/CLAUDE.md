# LSST/ZTF/ANTARES Alert Data Quality Pipeline

A data quality pipeline for ZTF (and eventually LSST) alert data via the ALeRCE and ANTARES brokers.

## Environment

- Python 3.13, venv at `.venv`
- Activate: `source .venv/bin/activate`
- Package managed with `uv`; install: `uv pip install -e .`
- Dev deps (pytest, pytest-mock): `uv pip install pytest pytest-mock`
- Key deps: `alerce`, `antares-client`, `pandas`

## Structure

```
src/rubin_qa/
    config.py          — constants and thresholds
    retry_budget.py    — run-wide retry sleep budget, shared by both clients
    client.py          — ALeRCE API wrapper (_api_call, fetch_candidates, fetch_object_data)
    antares_api.py     — ANTARES API wrapper (fetch_antares_candidates, fetch_antares_locus) + the ANTARES helpers the tools share
    validators.py      — validate_completeness, validate_antares
    classifier.py      — _version_score, _method_weight, classify_object, classify_antares
    reporting.py       — build_qa_row, run_pipeline, build_antares_qa_row, run_antares_pipeline
    profiler.py        — object_profile (diagnostic deep-dive, all three surveys) + its own CLI
    photometry.py      — broker-neutral fetch layer: PhotPoint / SurveyObject, ALeRCE listings + light curves (ZTF, LSST)
    sky_catalog.py     — Legacy Surveys DR10 tiles (cached in cache/), local host/star/AGN matching
    tns.py             — TNS lookups via ALeRCE's throttled TNS service (two-pair canary rule)
    transient_monitor.py — new-transient scan of a sky cone (own CLI: uv run python -m rubin_qa.transient_monitor)
    __main__.py        — CLI entry point
pipeline.py            — thin shim: uv run pipeline.py [survey] [page_size | oid ...]
tests/                 — pytest, mock data only (no live API calls)
    test_antares.py    — ANTARES path end to end; antares_api.py at 100% stmt coverage
    test_live_without_antares.py — the monitor's daily run with ANTARES impossible to import
    test_systemd_units.py — the monitor's unit: no arguments (live footprint, never --init), daily, Persistent
systemd/               — example user units (.example), lsst-<role>; setup notes in systemd/README.md
pyproject.toml         — build: hatchling, scripts: rubin-qa, rubin-qa-profile
```

### Runtime directories (gitignored; the user's rule, 2026-10-02)

- `cache/`: anything that can be fetched again. Deleting it only costs time. (DR10 tiles, atlas, bricks, maskbits; replay candidates, neighbours and light curves; the LSST box census rows and their checkpoint; the point-source S/N rows; the DES-SN5YR head file.)
- `state/`: anything that can't be recreated. Deleting it loses information. (The transient monitor's state per footprint, the point-source watch, the host tool's TNS sample and pending TNS lookups, the pre-fix TNS sample kept as evidence, the latency samples, the retired SSO monitor's state.)
- `logs/`: run output. It can be deleted at any time. (Run logs, replay results, host-matching scores and reports, TNS check results — all regenerable from `cache/` + `state/`.)

New files go by this rule, and a writer into `cache/` or `state/` writes a temp file and renames it. **Paths resolve from the repo root, never the current directory** (user, 2026-10-02): code and tools take every data path from `config.PROJECT_ROOT` (one root; `RUBIN_QA_ROOT` overrides it for both), and relative paths typed on the command line go through `config.from_root`, so a documented example such as `--csv reports/x.csv` works from any directory. Only the tools' `sys.path` bootstrap lines stay file-based (`Path(__file__).parents[1] / "src"`): they run before `rubin_qa` can be imported. Pinned by `tests/test_paths.py`. `reports/` is separate: published evidence, tracked in the repo.

## Pipeline stages

**ALeRCE (ztf/lsst):** `fetch_candidates()` → `fetch_object_data()` → `validate_completeness()` → `classify_object()` → `build_qa_row()` → `run_pipeline()`

**ANTARES:** `fetch_antares_candidates()` → `fetch_antares_locus()` → `validate_antares()` → `classify_antares()` → `build_antares_qa_row()` → `run_antares_pipeline()`

## Key design decisions

- `fetch_candidates`: deduplicates oids (ALeRCE API returns duplicates); default page size 100
- `fetch_object_data`: 3 API calls per object (detections, magstats, probabilities), each with retry (4 attempts, 9s base delay, exponential → 9/18/36s). Sized for ALeRCE 504 episodes, where the endpoint stays slow for tens of seconds.
- Failure messaging: operator-facing messages go to stderr with one of two prefixes from config.py — `WARN: ` (`WARN_PREFIX`) for degraded-but-recoverable conditions where the run continues (retry attempts, an empty candidate page), and `ERROR: ` (`ERROR_PREFIX`) for failures whose caller cannot proceed (failed candidate fetch, pipeline exception, no rows produced). Every ERROR path returns no data or exits 1. stdout carries only normal output (progress lines, QA table). A run that produces no rows writes no CSV and exits 1.
- `validate_completeness`: confirmed = ndet > 1; no magnitude threshold filtering. **`no_magstats` is not emitted for LSST** — ALeRCE raises `NotImplementedError` for every LSST object, so the token fired on 100% of rows, and since any issue makes `build_qa_row` return FLAG it forced every LSST object to FLAG and hid its real verdict (fixed 2026-09-12). A condition always true of a survey describes the survey, not the object. Restore it if ALeRCE ships LSST magstats.
- `_version_score`: accepts whatever the broker puts in `classifier_version` — ZTF sends strings (`"1.0.0"`), LSST sends ints (201, 202). An `isinstance(str)` guard used to score every LSST version at the neutral 1.0 (fixed 2026-09-12). Note the 0.20 cap saturates at raw ≥ 10, so any integer scheme ≥ v10 scores a flat 1.10; since the score multiplies every classifier's weight and consensus is a ratio, a value shared by all rows cancels out — LSST's 201-vs-202 still cannot be told apart. Rescaling the cap would move ZTF's tuned weights, so it is left alone.
- `classify_object`: weighted consensus — lc_classifier outweights stamp_classifier, gap widens with ndet; consensus ≥ 0.90 → clean, ≥ 0.65 + dissenters < 0.30 → minor flag, else genuine split
- `build_qa_row` status tiers (in priority order): FLAG if completeness issues or n_classifiers < 2 ("insufficient_classifiers"); PASS if consensus ≥ 0.90; REVIEW_MINOR if consensus ≥ 0.65 + outlier dissenters; REVIEW_MAJOR otherwise
- REVIEW_MINOR is currently dormant for ZTF: `lc_classifier` returns empty for most objects, leaving only stamp_classifier voting → n_classifiers=1 → FLAG (insufficient_classifiers). Will activate when lc_classifier data flows.

### ANTARES-specific design

- `fetch_antares_candidates`: deduplicates locus IDs (ANTARES API returns duplicates, same issue as ALeRCE)
- `fetch_antares_locus`: accepts ANTARES locus IDs (`ANT...`) or ZTF object IDs (`ZTF...`) — routes to `get_by_id` or `get_by_ztf_object_id` accordingly. Builds `ms` from locus.properties (num_mag_values, brightest/faintest_alert_magnitude). Filters `locus.alerts` to `ant_mag.notna()` rows only — upper limits (`ztf_upper_limit`) have no `ant_mag` and are excluded from the lightcurve.
- `ndet` uses `num_mag_values` from locus.properties (ANTARES quality-filtered count, conservative). `len(dets)` after filter may be slightly higher — ANTARES applies additional cuts not reflected in the raw alert stream.
- `classify_antares`: filters raw tags to `SCIENCE_TAGS` before computing consensus; pipeline/filter tags are stripped. `top_class` = all science tags sorted and joined (e.g. `"dimmers, extragalactic"`). consensus = 1/n_science_tags; single science tag → PASS; two or more → REVIEW_MAJOR; only pipeline/unknown tags → REVIEW_MAJOR with `no_science_tags` flag listing which pipeline/unknown tags were present; zero tags → FLAG (`no_classification` from `validate_antares`). REVIEW_MINOR is unreachable here: 1/n caps two tags at 0.50, under the 0.65 majority threshold.
- `build_antares_qa_row`: same output schema as `build_qa_row`; no `n_classifiers < 2` threshold (ANTARES uses tags, not multi-classifier votes). In ANTARES context, `n_classifiers` = number of *science* tags.
- `antares-client` must be installed; import is deferred (lazy) so ALeRCE-only users are not affected

### Transient monitor (transient_monitor.py, rebuilt 2026-09-27)

Broker-neutral: brokers are data sources, the monitor decides on photometry. Design origin: `transient_monitor_idea.md`, superseded where below differs.

- **No state is an error; `--init` is the first run** (user, 2026-10-02). The monitor reports changes relative to its state, i.e. what it has already reported; from an empty state everything that currently meets the rules looks new, even objects weeks old (the D replay's first day: 7 warm-up alerts). So a live scan without `state/transient_monitor_<footprint>.json` exits 1 with an `ERROR:` naming the path, before fetching anything: a missing or misplaced state file can never quietly behave like a first run and report everything again. `--init` makes starting from empty a deliberate act: it evaluates everything as usual and records it in the state as already seen, without reporting it (no alert list, no TNS lookups, no point-source watch entries; a summary by category instead), then creates the watch file. Refused when state exists (it would reset it and hide alerts) and with `--replay` (a replay keeps its state in memory). Trade-off, accepted: something genuinely new on exactly the init day is absorbed; it still shows up later if its category or path changes (the re-report rule). For ecdfs it hardly matters — LSST quiet there since March, ZTF barely reaches it. A missing watch file when the footprint has state is said (`WARN:` plus a report line: its evidence count restarts from zero), not an error: the watch never fails the run.
- **Daily unit** (`systemd/lsst-transient-monitor.service.example` + `systemd/lsst-transient-monitor.timer`, 2026-10-03; the user installs it). It reuses the SSO monitor's pattern (daily, `Persistent=true`) but logs to the journal like the other active units (user, 2026-10-03), with `PYTHONUNBUFFERED=1` so the report arrives line by line and in order with the `WARN:` lines. **Unit files are copied into the user's `~/.config`** (user, 2026-10-03): only comments that serve the copied unit stay in them (never `--init`/`--dry-run`, the hardening pointer); the explanations live in `systemd/README.md`. A timer holds no paths, so it has no `.example` and no comments, and **no time zone**: the hour is the installer's choice. The example's 16:00 is local time on a machine in Germany: ZTF's night (Palomar, sun at −12°) ends as late as 15:03 German time (late October), Rubin's by 12:43, and ZTF is the only live stream now. `ExecStart` takes **no arguments**, pinned by `tests/test_systemd_units.py`: the live footprint is the CLI default; never `--init` (a missing state stays an error); never `--dry-run` (alerts would repeat daily). `TimeoutStartSec=2h`, because a hung oneshot would make the timer skip every later day silently. Checked under the exact sandbox via a throwaway `systemd-run --user … --dry-run` (success, 49 s, state untouched).
- **Identity = survey object** (`ztf:ZTF26…`, `lsst:<diaObjectId>`), never a broker ID (an ANTARES locus is a place: one can hold ZTF18 + ZTF26 + an LSST object). State (`state/transient_monitor_<footprint>.json`) is keyed on these. **State lives in `state/`, not `logs/`** (2026-10-02): it holds what must outlive a run (reported pairs, parked onsets, the point-source watch's evidence), and `logs/` is the directory people clean up and rotate. Written temp file + rename. `state/` is gitignored; the retired SSO monitor's `bright_sso_state.json` moved there too (its `STATE_FILE` path constant changed, with the user's permission — nothing else in that script).
- **Fetch layer** (`photometry.py`): `PhotPoint(survey, survey_object_id, mjd, band, flux, flux_err, detected, broker)`, flux in nJy (difference image). Upper limit: flux NaN, flux_err = limit/5. LSST forced photometry: detected=False. **One broker, ALeRCE, for the whole live path** (user, 2026-10-03: one broker, one adapter, one set of failure modes): each survey's cone listing (`discover_alerce(survey, …)`; ZTF via the legacy client, whose JSON is a page dict with `items`, LSST via the multisurvey client, a bare list) and one `query_lightcurve` per object worth it (`needs_photometry`: n_det ≥ 2 and a recent onset or recent activity; ZTF detections + upper limits, LSST detections + forced photometry); a listed object not worth a call is rejected as `not_fetched`, never `no_detections`. Before, ZTF came from ANTARES loci, LSST from ALeRCE and TNS from ANTARES's crossmatch, which left every LSST object without a locus "not checked". Measured on ecdfs 2026-10-03: ZTF listing 38 objects in 1.8 s, 31 light curves fetched, 0 failed (ANTARES had listed 45 ZTF + 4 old LSST objects for the same window, counting loci active through upper limits). ANTARES now remains only in the QA pipeline (`antares_api.py`), the validation tool's TNS sample, the asteroid probe, and the retired SSO monitor. **Guarded** by `tests/test_live_without_antares.py`: it runs the daily command (`--dry-run`, ecdfs) in a fresh interpreter where `antares_client` and `rubin_qa.antares_api` cannot be imported, with only the network faked at its edges (ALeRCE's client methods, `requests.get` for Data Lab and the maskbits portal, `requests.post` for the TNS service; any other connection raises), and fails on any import attempt, even one a `try/except` swallows. Its fake day has one bracketed ZTF transient on a DR10 galaxy and in TNS, so every stage runs. Checked by injecting ANTARES at four places (a module import, the TNS stage, ZTF photometry, DR10 `classify`; two of them swallowed): all four caught. Replay D rerun after the switch (2026-10-03): identical 43 alerts + 3 notes, every field — the replay always took its ZTF neighbours and light curves from ALeRCE, so the bracketing source did not change.
- **Footprints are cones, everywhere** (ALeRCE only searches cones): `(ra, dec, radius)`, membership = angular separation ≤ radius, so no declination correction, no RA 0/360 wrap, and every margin is radius + 1°. Presets ecdfs (53.1, −27.8) — **the live footprint, decided 2026-10-02** (`LIVE_FOOTPRINT`, the CLI default when neither `--footprint` nor `--cone` is given; it goes live while Rubin is still off sky, hence the LSST listing guard below) — D (150.1, 2.5; COSMOS test replay, Rubin data Feb–Jun 2026) and C (35.7, −9.0; former live candidate v1); radius 2.82° = 25 deg². ANTARES's cone (used only by the tools now) = its own `sky_distance` query clause, hand-built since elasticsearch-dsl cannot: `antares_api.sky_distance_clause`. The last box in the code, the DR10 brick list, became a cone on brick centres 2026-10-02 (user: one shape, so nothing can quietly keep using the other). Not footprints, so not cones: the 0.1° catalogue tiles and DR10's bricks themselves (how the catalogue is cut). **Deliberate exceptions — do not "fix" them:** `tools/atlas_query_contract.py` fetches an RA/Dec superset box on purpose: it is the oracle for the fake's q3c reading, and an oracle has to be independent of the thing it checks. `host_match_check.random_positions` places tiles with a flat-sky step (cos(dec) at the centre): ~±2.5% density skew across ecdfs, membership still an exact cone. Its bias on the chance-host rate is at most ~0.1 pp against the rate's own 0.93 pp error (14.8% of 3000 positions; tile-clustered — 25 positions per tile, design effect 2.1, so the binomial 0.65 pp understates it). Make it exact the next time the random stage reruns for another reason (e.g. a new footprint), when it costs nothing extra. The 2026-10-01 census is box-based and kept as run.
- **new**, per survey on its own history: first detection within N=14 d, ≥ 3 detections over > 1 night, a quiet point within X=10 d before it with 5·flux_err < first-detection flux. LSST can never bracket its own onset (forced photometry starts at/after the first detection), so an LSST onset may be bracketed by a ZTF upper limit on an associated ZTF object (`bracketed_by_ztf`) — rarely deep enough. Depth is tested against the *first* detection — **decided 2026-10-02, stays**: bracketing claims the object was not there at the brightness of its first detection, so the quiet point must have been deep enough to see it at that brightness. Against the brightest-so-far (measured: 88% vs 45% of new ZTF objects bracketed) a shallow quiet point would pass — a ZTF limit of 20.5 against an LSST object first seen at 23 that later passes 20 would count as bracketed, which proves only that it rose, not when it started; `rising` already covers that case.
- **Every path needs detections on more than one night** (`spans_nights`, ≥ `MIN_SPAN_DAYS` 0.5 d), checked first in `evaluate` (2026-10-01): `rising` could pass on one night of detections plus brighter forced photometry, and `rapid_rise` on two detections the same night. Cost: a genuine transient is reported on its second night instead of its first. It is also what makes the replay's span cut lossless.
- **rising** (main LSST path): recent onset, same band, earliest vs latest post-onset flux (forced included) ≥ 3σ and ≥ 0.3 mag over ≥ 0.5 d. **rapid_rise**: ≥ 1 mag within 3 d, any age (old object → `re_brightening`); ordinary SNe are too slow for it.
- **unbracketed**: parked, re-judged each run, expires when the first detection leaves the window.
- **One event, one alert** (2026-10-02): another survey's detection within `ASSOC_RADIUS_ARCSEC` (1.5″) of an object already reported becomes a *note* on that alert, not a new alert (`judge_day` → `DayResult.notes`, printed under "the same events, seen by another survey"; replay records carry `note_on`). Candidates are taken in order of first detection, so the survey that saw the event first holds the alert; the note keeps its own category and path (in the replay the later ZTF detections were `bracketed`, stronger than the LSST `rising`). Matched on positions kept in the state (`reported[key]` has `ra`/`dec`), not on the day's listing, so it holds on a day the first survey's listing failed. Same-survey neighbours are a recurrence (context lines), not grouped. Replay D: 46 → 43 alerts + 3 notes (2026ezw, 2026fgl, 2026ivl, pairs 0.26–0.34″ apart).
- **TNS in the live report** is display context, looked up after the verdicts at ALeRCE's TNS service (`_add_tns` → `tns.tns_lookup`, the throttle-safe two-pair rule; since 2026-10-03, every object by position, no "not checked" any more). Every alert carries a TNS line: the record (`SN 2026abc, SN Ia, discovered …`, matched within 2″); `none yet; asked again each run for 30 d`; or `unavailable (lookup failed); asked again …`. **"none" is re-asked like "unavailable"** (user): it only means nobody had reported the object yet — SN 2026kfw's TNS report came 5 days after our replay alert. Both go into the state (`tns_watch`, positions kept) and are asked again every run for `TNS_RECHECK_DAYS` (30) with one paced call each (6.5 s, no canary: an empty answer only means "not yet" whatever its cause; only a record is news). A record that appears is printed under "TNS for earlier alerts" with its lag (`… (5 d after our alert)`); after 30 d: "no TNS record 30 d after the alert; no longer asked". Any exception in a lookup is caught: never fails the run. A state from before 2026-10-03 is read and rewritten: `lsst_newest_mjd` → `newest_mjd` per survey; the old ANTARES-locus `tns_pending` entries cannot be asked by position and are dropped.
- **Filters**: galactic plane, and LSST's own asteroid ID (`ssObjectId`, carried by ALeRCE's light curves). Nothing is filtered on the sky context (a Gaia star used to be dropped unless moving; since 2026-10-01 it is reported as `stellar` on every path). Broker classifications and TNS are report-only. **Known gap since 2026-10-03:** ALeRCE's ZTF detections carry no `ssnamenr`, so ZTF has no asteroid ID any more. The two-night rule covers almost all of it: of 61 loci made only of asteroid detections in the 2026-09-27 probe, 60 fell on a single night; the one left was two different asteroids crossing the same position on different nights (1 in 159 new high-|b| loci), which a ZTF object can also collect, since ZTF associates by position too. Such an object would surface as an alert a human can dismiss, not vanish.
- **Decision table** (`SKY_CATEGORY`, user's design 2026-10-01): two separate axes. The **sky context** (DR10 verdict + AGN flag on the assigned source) alone decides the category, whatever the path: `host` (incl. `agn_host`, a context note), `agn` (`agn_nuclear` on a host or point source), `orphan` (none), `point_source`, `stellar`, `unchecked` (catalogue gap or unavailable). The **path** — `bracketed`, `rising`, `rapid_rise`, `re_brightening` — is the confidence label (`Candidate.conditions`); a report reads `host · rising`. Names claim only the sky: `new_candidate`, `agn_flare`, `stellar_flare` claimed a path too (the replay's "flaring" stars rose over up to two weeks — stellar variability). Every combination leads to a visible category, no "dropped" cell; `sky_context` raises on a verdict/flag combination missing from the table. Re-reporting keys on the (category, path) pair (state field `pairs`): a new path *or* a new category is news — above all `unchecked` becoming a real verdict once the catalogue is available. Tests enumerate all 5 path cases × 8 sky contexts through `evaluate`. Before 2026-10-01 a rising star, a rising AGN and a rising point source were all just `rising`, mixed with supernova candidates — a combination nobody had written down.
- **DR10 matching** (`sky_catalog.py`): tiles of 0.1°, fetched on demand from Astro Data Lab TAP and cached (per catalogue version) — the deep fields hold ~7M rows per 25 deg² (~2M at r < 24), so whole-box download is impractical. Verdicts in order (2026-10-01): `stellar` (Gaia parallax or PM ≥ 5σ within 1″) → `point_source` (nearest non-piece source within 1″ is a PSF; before host, because a point source within 1″ is closer, more specific evidence than a DLR association — a faint variable beyond Gaia on a galaxy's outskirts must not pass as SN-like; measured cost: 1.4–2.6% of random positions, 4 of 166 known hosts) → `host` (directional light radius ≤ `HOST_DLR_MAX`, flagged `nuclear` within 1″ of the centre, 2″ for atlas hosts) → `none`. **No S/N floor on the point-source rule — measured 2026-10-02, left as measured (user's decision):** `tools/point_source_snr.py` (report `logs/host_check/psf_snr_report.txt`) fetched flux/flux_ivar g,r,i,z and `dchisq` for all 82 firings of the rule. Two-sided on combined S/N: floors 6.5–7 lose none of the 12 point-like true hosts (faintest 7.1; from 7.5 they fall, 5 of 12 at 10) and lower the random point-source rate 2.03% ± 0.26 → 1.73/1.67% (under 1.5σ); neither recovers the 4 relabelled correct hosts (S/N ≥ 16). Both edges of the window are single objects, and the cost on faint real variables/QSOs is unmeasured. Known limitation: SN 2026kfw (spectroscopic Ia, replay D) stays `point_source` on a DR10 PSF of S/N 6.3 (r = 26.1); a floor would make it `orphan`, not `host`. A floor is in S/N, never magnitude: DR10 measures r for sources detected in other bands (a faint red galaxy reads r ≈ 26 at high S/N; one host PSF at r = 26.4 has S/N 175), and depth varies across the sky (DES deep stacking in ECDFS). **Point-source watch** (`point_source_watch`, called by the daily report and every replay, user 2026-10-02): every `point_source` alert (live or replayed) goes into `state/point_source_watch.json` (shared by all footprints and replays; not subject to the state's 60-day retention) and is looked up in TNS (`rubin_qa/tns.py`, two-pair canary rule) weekly per alert until classified, or until 180 d after the alert. Only spectroscopic supernovae count, judged on TNS's classification **type**, never the prefix (`SUPERNOVA_TYPES`: "SN…", "SLSN…"; unclassified = AT with type `{id: None, name: None}`; AT 2018hyz, a TDE, comes back with prefix `TDE`, checked 2026-10-02). Any other class settles the alert and is said in the report, never dropped silently, with a note for the nuclear types (`NUCLEAR_TYPES` TDE, AGN, QSO: the cases the label exists for), and tallied in the watch line; for those the point source's combined g,r,i,z S/N is fetched (`sky_catalog.counterpart_snr`: the tiles carry no optical flux_ivar). Distinct TNS names below S/N 7 (`PS_REVISIT_SNR`) are counted: one is kfw, two can be coincidence, `PS_PATTERN` = 3 is a pattern — then a NOTICE in the report every run, asking to measure the floor again. Findings carry a fingerprint of the point-source rule (`point_counterpart` + `_verdict` source + radius), so changing the rule or `PS_PATTERN` is what stops the notice. The report always carries one watch line (count, awaiting, unavailable lookups); it never fails the run, and `--dry-run` writes nothing. Negative result kept: "PSF" is not specifically unreliable at low S/N — the PSF and best extended fits sit within dchisq 1 for 67–78% of these sources in every S/N bin. No compact-host rule: measured and dropped 2026-10-01 (0 of 14 point-like hosts gained, 10.4% of random positions given a host at 3″; 12 of 14 sit within 1″, where `point_source` keeps them out of the orphans). AGN is a flag on the assigned source, not a verdict (`agn_nuclear` within 1″ → monitor category `agn`; `agn_host` → a context note): WISE W1−W2 ≥ 0.16 AB (= 0.8 Vega, Stern+2012) only when both bands have S/N ≥ 5, else stated as 'no measurement', never 'not AGN'. No Milliquas match is wired in. **Pieces belong to their atlas galaxy in every rule:** any row inside an atlas ellipse (maskbit 12) other than the galaxy itself — the frozen `L3`/−1 pieces and the point sources fitted on top (NGC 873's nucleus: a PSF 1.3″ off the model centre, `ref_cat` empty) — is excluded from the host search and the point-source rule, so a transient on a nucleus becomes host + `nuclear`. `HOST_DLR_MAX` = 4 and `ATLAS_RADIUS` = `sma_moment`, chosen 2026-10-01 from `tools/host_match_check.py` (21 TNS + 172 DES-SN5YR known hosts vs 3000 random positions; at 4, 99% of DES hosts get a host and 86% agree with DES, 14.8% random chance; hosted SNe outnumber hostless ~20:1, so false orphans cost more than chance hosts). Report: `reports/host_match_validation_20261001.txt` (fingerprinted); README section "Host Matching Validation". `point_source` before `host` decided 2026-10-01 on a 4-vs-4 tie on known hosts (it relabels 4 correct hosts; host-first would give 4 of 12 point-like hosts a wrong galaxy): a wrong host asserts something false, `point_source` only withholds a host label and the transient is kept either way, and the order keeps faint variables from passing as SN-like.
  - **Ellipse conventions (verified 2026-10-01, do not "fix" from the docs):** major axis at 0.5·atan2(e2, e1) East of North; `shape_r` = half-light radius *along the major axis*. The DR10 catalogue page's PA = 180 − ϕ is the mirror image, and the atlas table's "clockwise from North" for its `pa` is wrong the same way. Evidence: pixel second moments on FITS cutouts with WCS orientation (60 galaxies: 92% within 15° vs 2% for the docs; `tools/pa_from_pixels.py`), Legacy cutouts by eye, Tractor's `EllipseE.getRaDecBasis`, 609 HyperLeda PAs. Anchored in tests: fixtures whose expected axis was read from the image (5 Tractor-path, 3 atlas-path); flipping to the docs formula fails them.
  - **Siena Galaxy Atlas:** DR10 marks atlas galaxies `REF_CAT = L3` with `REF_ID` = SGA_ID; the other sources inside the atlas ellipse are also `L3` with `REF_ID −1`. Those pieces (~4–7 per atlas galaxy, up to ~75 within 60″ of a big one) are excluded as host candidates. The atlas galaxy uses the atlas's own measured ellipse (`sga2020.ellipse`, LEFT JOINed into every tile query) only where it was measured (`sma_moment > 0`); otherwise `pa`/`ba` are HyperLeda copies and the Tractor shape is used. Radius scale is a choice (`ATLAS_RADIUS`): `sma_moment` runs ~2.6× `shape_r`.
  - **Host candidates in two steps** (2026-10-01): no fixed radius is both cheap and large enough for a galaxy arcminutes across (SN 2025zi is 123″ from NGC 1398). Step 1 = Tractor extended sources within `SEARCH_RADIUS_ARCSEC` (30″, 0.1° tiles); step 2 = every atlas galaxy with separation < `HOST_DLR_MAX` × its major-axis radius — exactly those that *can* reach d_DLR ≤ threshold, since r_dir ≤ a. The atlas is fetched once per footprint (`footprint_atlas(cone)`: one q3c cone query, cone radius + `ATLAS_MARGIN_DEG`, ~900 galaxies, ~1 min) and step 2 filters it in memory. The monitor loads it lazily on the first DR10 lookup (`footprint_classifier`); if it fails, the run continues with step 1 and warns once.
  - **Margin 1°**: within 5° of every footprint edge no atlas galaxy has D26/2 > 15′ (largest 6.2′, ESO 358-063), so 4 × a < 0.42° even on the most generous radius. Widen if a > 15′ galaxy ever sits near a footprint.
  - **Cache keyed on catalogue versions**: `cache/ls_dr10+sga2020/{tiles,atlas}/`, derived from `TABLE` and `ATLAS_TABLE`, so a new Legacy or atlas release refetches instead of mixing versions. A cached file missing a column is refetched too.
  - **Catalogue gaps (DR10 BAILOUT):** where DR10's fitting gave up (maskbit 10) no sources were written, so empty sky there is not an orphan. Measured on brick 0532m280 (CDFS centre, deepest DES stacking): 49% of its pixels BAILOUT, its empty 36″ cells 97% BAILOUT, and no surviving row sits on a BAILOUT pixel (so the rows' own maskbits can never show it). `catalogue_gap(ra, dec, bricks)` checks the maskbits images (portal, one per brick, cached) of every brick overlapping step 1's 30″ search area for any BAILOUT pixel, or part of the area in no brick — the area, not the point, because a host centred in a gap is lost even when the SN is outside it → `classify(coverage=...)` returns `unavailable`, never `none`. The monitor loads the footprint's brick list (`footprint_bricks`: one q3c cone on brick centres, radius + 1° — checked against Data Lab 2026-10-02: identical to the old box list's centre-in-cone bricks, C 736 / D 738 / ecdfs 732, and none of the ~450 bricks touching each footprint + 30″ missing) with the atlas; without it every crossmatch says "catalogue gaps not checked". Step 2 is unaffected: the atlas table and the L3 join hold the same galaxies in all three footprints (C 768, D 1173, ecdfs 1002), since DR10 fits atlas galaxies apart from the blob fitting that bails out (checked by `tools/atlas_query_contract.py`). 14 of 413 cached tiles have such gaps, clustered at the CDFS centre — matters if ecdfs becomes the real footprint; backfilling from DES DR2 only if the gap count proves large.
  - **Fetch failures never become data:** errors raise `CatalogError` and are never cached; an empty answer is returned but not cached (a genuinely empty tile just refetches); requests send an explicit `MAXREC` and a result at it is rejected as truncated (CSV carries no TAP OVERFLOW status); maskbits accept only a FITS body, 404 = no brick (not cached). Each failure path has an injected-failure test. **Cached files are checked on read** (2026-10-02): a damaged tile or maskbits file is warned about, deleted and fetched again (`DAMAGED_FILE_ERRORS`), never a crash; `tile_is_cached` reads the whole file, since a truncated gzip keeps its header. Measured by truncating cached files: a gzip tile cut anywhere raises `EOFError` (the trailer holds length and CRC, so it can never read back as a shorter tile); a maskbits file cut inside its MASKBITS image raises (344 cuts over 3 bricks, never a silently wrong image), cut after it reads back identical (only the WISE masks after it are lost). Audit 2026-10-02: 1,266 current tiles + 203 older-schema (refetched on use), 514 maskbits, 6 atlas/brick lists, 0 damaged. The prefetches (replay `catalogue_needs`, `host_match_check.prefetch_maskbits`) ask `maskbits_is_cached`, not mere existence: a header-only completeness test (file at least as long as `fileinfo()` says for the last image, and a 2-D image present — the image check was added after a sweep found 27 cuts that left only the empty primary header "complete"); ~ms against ~0.2 s for a full read; swept over 1,064 cuts on 5 bricks, every "complete" one reads back identical. All cache writes are temp file + rename (same directory), which protects against a killed process; without fsync a power loss could still leave a short file, which the checked reads then refetch. Confirmed live 2026-10-02 on damaged temp copies: tile, maskbits and light curve each refetched identical; a simulated Ctrl-C mid-write leaves only an unread `.tmp`.
  - **`tests/fake_tap.py`** applies the q3c cone of the query it receives; its reading of q3c (argument order, degrees, great-circle ≤ radius) was checked against Data Lab by `tools/atlas_query_contract.py` (footprint D, margin included: 1173 = 1173 atlas IDs, edge cut exact at 3.82°). On demand, outside the suite; rerun if the footprint query changes.
- **Replay** (`replay.py`, `--replay FIRST_DAY LAST_DAY`; rebuilt 2026-10-01 to the user's design, `--as-of` removed). The LSST stream stopped 2026-07-14 (summit evacuation), so replay is the only way to exercise the LSST path. The old `--as-of` filtered on summary fields read *today* (ANTARES newest alert, ALeRCE last detection): a footprint-D replay as of 04-15 would have fetched 8,105 LSST light curves, 6,453 only because of detections after that date. Now it filters only on what cannot change: candidates = objects first detected in [first day − 14 d, last day] (ALeRCE LSST + ZTF listings in ≤ 7-day chunks), cut to detections spanning > 1 night (lossless by the rule above: a span only grows; `n_det ≥ 3` is *not* lossless, since `rising`/`rapid_rise` accept 2 detections). One cached light-curve fetch per candidate (`cache/replay/`, failures never cached). Every replay cache file (candidate lists, ZTF neighbours, light curves) is written to `<name>.tmp` and renamed, and every read checks it (parses, expected shape; light curves must build `PhotPoint`s): a damaged file is warned about, deleted and fetched again — never a crash, never data (2026-10-02, after an aborted `--compare-cuts`; the cache was validated then: 3,603 files, 0 damaged, the only file written by the aborted run complete). Before judging, every DR10 tile and maskbits brick the crossmatch can need is prefetched (4 workers, retries) — only for candidates whose detections span > 1 night, since nothing else reaches the crossmatch, so an uncut run needs the same tiles. The first real run (2026-10-01) judged from a cold cache, fetching tiles one by one in the day loop: it was at day 32 of 65 after 2.5 h of wall-clock time — at least 1 h of which the machine was suspended — with Data Lab measured slow (> 2 min per tile) then down (502) right after; each lookup that failed (a timeout, or a connection broken by the suspend) became an `unavailable` crossmatch for the rest of the run. That run was discarded. Then each day is judged by the live code (`judge_day`) on light curves sliced to that day, 0 API calls per day; crossmatches that could not be made are counted in the summary and the JSON, never passed as results. ZTF objects of any age at an LSST candidate's position are fetched as association *context* only (to bracket LSST onsets), never judged. Out of scope: old objects re-brightening — covered by synthetic-light-curve unit tests. `--estimate` lists and prints the time estimate without fetching (light curves at 1.13 s per call measured; DR10 tiles at 3 s each over 4 workers, valid only for a healthy Data Lab); `--compare-cuts` is the equivalence test (same window with and without the cut must give identical alerts). **Cost gate** (2026-10-02): `replay.price()` lists and estimates; `--compare-cuts` prices *both* sides before either fetches, and above `CONFIRM_THRESHOLD_SECONDS` (900 s) a replay asks y/N on a terminal and refuses without one unless `-y/--yes` (a replay is never scheduled, so a non-interactive many-hour start is a mistake; unlike the QA pipeline's units, which proceed). Before it, each side priced itself only when it started, so a full-window `--compare-cuts` started the 41,542 + 9,042-candidate uncut side unasked. The estimate omits the ZTF neighbours' own light curves (unknown until the neighbours are fetched). Footprint-D numbers: 03-12 → 05-15 ≈ 381 LSST candidates; 02-15 starts would pull in the first-look burst (≈ 42k). **Results 2026-10-01** (README "Replay Validation"): 477 candidates, 46 alerts in 65 days (host 29, agn 6, stellar 6, orphan 4, point_source 1; since the 2026-10-02 grouping 43 alerts + 3 notes), 0 fetch errors / unavailable / suspended; rerun from cache ~1 min. `--compare-cuts` 04-05→04-06: EQUIVALENT (48 vs 2,200 candidates, 1 alert — narrow evidence). TNS (`tools/replay_tns_check.py`): ZTF host·bracketed 6/6; LSST 22/32, all discovered from Rubin data and reported by SGLF/Lasair/ALeRCE (internal name `LSST-AP-DO-<diaObjectId>`), so the LSST rate measures broker reporting practice, not the monitor's selection.
- **ALeRCE LSST listing can fail silently**: a heavy query (long first-detection window over footprint D) sometimes answers 200 with zero items, sometimes 504, sometimes data after ~40 s (2026-10-01, same 30-day query). The replay lists in ≤ 7-day chunks and re-asks an empty chunk day by day. **The live monitor guards both listings** (`check_listing`, LSST 2026-10-02 — the user's first priority before ecdfs went live — and ZTF since 2026-10-03, same server, same failure; the newest per survey is `newest_mjd` in the state; ZTF's newest-in-cone query takes ~1 s): with Rubin off sky an empty listing is the normal state for weeks, so it must not look like a failed one. Every failure prints `LSST listing (ALeRCE): FAILED - …` plus an `ERROR:` line and exits 1, after the ZTF side is reported and the state saved (a missed listing loses nothing: parked objects stay parked, the 14-d window lets the next run catch up). Measured 2026-10-02: `total` in the response is not a count (it reads page_size + 1); the filtered newest-in-cone query takes ~2 s on ecdfs but took 59.5 s once on D; ALeRCE's newest LSST detection is 2026-03-09 in ecdfs and 2026-06-14 in D.

## Survey / broker support

- `survey="ztf"` (default) — ALeRCE, full support: magstats, classifiers, detections
- `survey="lsst"` — ALeRCE multisurvey. `query_magstats` raises `NotImplementedError`; ndet/mag stats fall back to raw detections. `query_classifiers`/`query_classes` are also unimplemented, but **`query_probabilities` works** and returns two ranking-1 classifiers (`stamp_classifier_rubin_beta` v201 and `stamp_classifier_rubin_beta_20260421` v202), so `classify_object` gets `n_classifiers=2` and the weighted-consensus path actually engages — unlike ZTF, where it collapses to 1. Caveat: the two are the same model at two dates, so their agreement is not independent evidence the way lc-vs-stamp would be. `query_lightcurve`, `query_detections`, `query_non_detections` and `query_forced_photometry` all work. LSST oids are integers from the API, normalized to str in `fetch_candidates`.
- `survey="antares"` — ANTARES broker: tag-based classification, locus model; requires `antares-client`
- Run ANTARES: `uv run pipeline.py antares [page_size | locus_id | ZTF_oid ...]`

## Known API quirks

- ALeRCE: `lc_classifier` returns empty for many objects; `stamp_classifier` works reliably
- ALeRCE: API returns duplicate oids — handled in `fetch_candidates`
- ALeRCE: LSST multisurvey client raises `NotImplementedError` for `survey="ztf"` — ZTF uses the legacy client path
- ALeRCE's TNS service (`tns.alerce.online/search`, POST ra/dec, no credentials) runs on a **quota of 10 answers per 60 s window and answers 200 with an empty record once it is spent** — throttling looks exactly like "not in TNS". Measured 2026-10-01: exactly 10 full answers per window; windows turn at :23 past the minute (not on it — don't rely on the phase); paced at ~7 calls/min, every answer full. The earlier "intermittent empty records" (2021bwv empty/full/empty) were our own 1 s pacing spending the quota. Lookups pace at `TNS_PAUSE` 6.5 s and accept an empty answer only when two (empty answer, full canary SN 2025zi) pairs fall within 60 s (`rubin_qa/tns.py`, moved there from `tools/host_match_check.py` 2026-10-02 for the monitor's point-source watch; tests in `tests/test_tns.py`): at most one window turn fits in that span, so one pair shares a window, and within a window answers only go full → empty. The rule never uses the phase (a restart can move it); it assumes fixed windows ≥ 60 s. `test_throttling_is_never_taken_for_not_in_tns_whatever_the_window_phase` sweeps 120 phases × 21 times at which other users spend the quota against a simulated service; a one-pair rule and a wall-clock-minute rule both fail it, and so does the real rule against a 25 s window (27 of 2520 cases). Structural limit: the proxy turns throttling into "not found"; if TNS becomes more than display context, a free TNS account (own API key, or the daily public-objects CSV as a local snapshot, which would also give a replay TNS as of each simulated day) removes the ambiguity.
- **ANTARES code lives once** (2026-10-03): the helpers everything in the repo still needs — `antares_errors()`, `is_solar_system`, `locus_survey_ids`, `sky_distance_clause` — are defined in `antares_api.py` and imported by the tools (`asteroid_probe.py`, `host_match_check.py`); `tests/test_antares.py` fails if a tool re-implements one. Two copies drift apart, and a fix in one quietly misses the other — the same two-implementations problem as the two TNS paths had. **Deliberate exception — do not "fix" it:** the retired SSO monitor (`antares_sso_monitor.py`) keeps its own self-built ANTARES code and stays out of the shared module. It is an artifact (user, 2026-10-03): not in use, with no plan to reuse it — a future SSO monitor would probably be built on the Fink broker, as new work. That duplicate is harmless: a frozen copy cannot drift, because it never changes, and `tests/test_sso_frozen.py` makes that true by construction — it pins the SHA-256 of the monitor's files (the script and its two systemd unit examples) and of the one function it imports (`config.now_mjd`), and that the script imports nothing else from the package. Recording a new hash there is the deliberate unlock, like the rule fingerprint in the point-source watch.
- ANTARES: credentials required for Kafka streaming; search/fetch API is open (confirmed). `get_by_ztf_object_id`, `get_by_id`, `get_random_locus_ids` all work without auth.
- ANTARES: `get_random_locus_ids` returns duplicates — deduplicated in `fetch_antares_candidates`. Expect **10-15% fewer IDs than requested** (measured 2026-08-06: 256 raw → 217/225/228 unique). Cause is upstream: the ES query uses `random_score` with no seed, and `_list_all_resources` issues a fresh request per page, so ordering reshuffles mid-walk and loci recur across pages. `run_antares_pipeline` emits one row per deduplicated ID unconditionally, so `len(df)` == unique count — a short report is this, not a row-drop.
- ANTARES: an ANT locus ID that does not exist answers **500, not 404**, so it is indistinguishable from a transient server fault and costs the full retry backoff. `get_by_ztf_object_id` correctly returns None → `locus:not_found`.
- ANTARES: `fetch_antares_candidates` / `fetch_antares_locus` retry via `antares_api._api_call` (same 4 attempts / 9s exponential as ALeRCE), on `requests` exceptions and `AntaresException`. ANTARES imposes its own 60s read timeout; before the retry existed, one slow morning meant the daily run produced no CSV at all.
- Retry is per-object in **both** brokers, so an outage multiplies across the page — ALeRCE worst, at 3 retried calls per object. Three ceilings bound it, applied to `run_pipeline` and `run_antares_pipeline` alike. All degrade rather than abort:
  - `REQUEST_TIMEOUT` (60s) — forced onto the ALeRCE client by `client._force_session_timeout()`, which wraps `Session.request` on all **five** sessions the Alerce object holds (top-level + legacy/multisurvey × search/stamps). The alerce package passes no timeout at all, so requests would block forever; the per-run ceilings are checked *between* calls and cannot interrupt a blocked socket. **It bounds inactivity, not call duration** — `requests` applies the timeout per socket operation, so a trickling response never trips it: the campaign caught three LSST calls *succeeding* at 60.7/60.7/63.3s with the ceiling in force. It reliably kills a dead connection (11 ZTF `ReadTimeout`s in 329 runs); a slow-but-alive one is bounded only by the run deadline. antares-client applies its own 60s timeout, so it needs no equivalent.
  - `RETRY_BUDGET_SECONDS` (300s) — total retry *sleep* per run, held in `retry_budget.py` and shared by both clients (a run stalls once, regardless of broker). Each pipeline calls `retry_budget.reset()` before its loop; `_api_call` draws on it via `consume()`, which clamps to what is left so the cap is exact. Once spent, attempts continue with no backoff.
  - **Run deadline — derived per job, not a constant.** `deadline_for(n, survey)` = `DEADLINE_SLACK` (6×) × `estimate_runtime()`, floored at `DEADLINE_FLOOR` (300s), computed from the *resolved* object count after dedup. `max_run_seconds=None` (default) means derive; `0` disables. A 1000-object ZTF scan is entitled to its ~1h; what trips is a run dragging far past its own estimate, i.e. a stalled broker or link. The slack is 6× rather than 3× because it absorbs what one pathological object can cost: the retry budget caps retry *sleep*, not socket time, so a worst-case ZTF object can block 3 calls × 4 attempts × 60s = 720s with only this deadline to stop it — see below.
- `SECONDS_PER_OBJECT` (config.py) holds measured per-object cost — ztf 3.7s (3 ALeRCE calls), lsst 2.4s (magstats short-circuits client-side), antares 1.0s. Feeds both the estimate and the deadline; update if broker latency shifts. Affects only pacing, never correctness.
  - **Settled 2026-09-01 by the sampling campaign** (329 samples, 2026-08-11 → 2026-09-01, ~1600 object timings per survey). Per-run medians: ztf p50 3.38 / p95 3.75 / p99 3.84 / worst 4.31; lsst 2.19 / 2.38 / 2.50 / 2.71; antares 0.93 / 1.36 / 1.45 / 1.53. Each constant sits at or above its survey's p95, so a typical run finishes inside its estimate — **no change needed**. The 17.0s ztf figure from 2026-08-06 never recurred in 21 days: it was an episode, not a baseline. Latency is flat by hour (3.19-3.61 across the 19 hours sampled), flat by weekday, and free of collection bias (timer 3.34 vs manual 3.41). Hours 02-06 are unsampled by choice — the machine is off overnight, so no run is ever issued then.
  - `DEFAULT_SECONDS_PER_OBJECT` (17.0s) does *not* track the table — it stays deliberately pessimistic for an unmeasured survey, since a new broker is likelier to be slow than fast. **It is a judgement call, not a measurement**: 17.0 was ALeRCE's 2026-08-06 ztf figure, which the campaign showed to be an episode, so only the pessimism survives. Also **currently unreachable** — the table covers every survey the CLI accepts, so the one live path to it is `__main__`'s untyped `survey` positional (`pipeline.py 50` parses `50` as a survey name). `choices=` on that argument closes the hole; re-derive the value when a fourth broker actually arrives.
  - Re-measuring: `tools/bench_latency.py` times each client call directly (no retry wrapper), 10 objects per survey, two rounds. What matters is per-object cost *excluding* the one-off candidate fetch, which `SECONDS_PER_OBJECT` does not model.
  - **Sampling campaign (2026-08-11 → 2026-09-01, concluded; hourly timer retired 2026-09-01 — re-enable `systemd/lsst-latency-sample.service.example` + `.timer` only to re-measure after a broker change):** `tools/sample_latency.py` appends one record per run to `state/latency_samples.jsonl` (~2.5 min; `--quick` skips the candidate fetch, ~1.5 min). Collected by an hourly systemd timer with `RandomizedDelaySec=3600` (`systemd/lsst-latency-sample.*.example`, now disabled), which landed one sample inside each hour; manual runs at odd hours work too and mix in fine, and measurably do not bias the result. It fills only the hours the machine is up — 02-06 stayed empty across the whole campaign, which is expected and not a defect. Each record keeps every individual object timing, and `--report` pools them across runs, so sample size does not track how often anyone remembers to run it. Records also store the `SECONDS_PER_OBJECT` in force at sampling time, so changing the constants mid-campaign does not corrupt the history. Broker failures are recorded as samples rather than aborting the run — they carry no timing, so `--report` lists them separately (12 across 329 runs: 11 ZTF `ReadTimeout` at the full 60s `REQUEST_TIMEOUT`, clustered 08-12→08-16 and 08-31, plus one 2026-08-13 13:30 event where ZTF *and* LSST both returned `APIError: 500` — the only broker-wide blip in the window. ~3.4% of ZTF runs; the broker really does swing). The timer runs `Persistent=true`, so records carry `uptime_s`/`source` and `--report --exclude-boot` drops boot-adjacent catch-up runs at analysis time. Note `state/` is gitignored — samples are local-only.
- The candidate fetch is unmodeled by `SECONDS_PER_OBJECT` and is the slowest single call in the system: ZTF `query_objects` measured p50 19.3s / p95 30.9s / max 45.4s (98 samples, 2026-08/09), against a 60s `REQUEST_TIMEOUT`. It is also *slower* at page_size=10 than at 100 — server-side variance dominates, page size barely matters. This call, not the per-object ones, is what keeps `REQUEST_TIMEOUT` at 60s.
- Profiler: `uv run python -m rubin_qa.profiler [survey] oid [oid ...]` (or `rubin-qa-profile`). Prints classification verdict, per-band photometry and a light-curve summary for one object. Per-band photometry is real magstats on ZTF and **derived from detections** on LSST and ANTARES, neither of which serves magstats. ZTF reports `magpsf_corr` coverage; LSST reports `reliability`/`snr` and forced-photometry epochs; ANTARES reports `ant_mag_corrected` coverage and source surveys.
- ANTARES: `locus.lightcurve` is a 14-column frame holding detections *and* upper limits together — `ant_mag` is null on a non-detection, where `ant_maglim` carries the limit. `ant_mag_corrected` is the `magpsf_corr` analogue; `ant_passband` the `fid` analogue. Also available: `locus.timeseries` (~114 cols), `locus.catalog_objects` (crossmatch), and ~20 precomputed `feature_*` entries in `locus.properties`.
- ANTARES: `ant_survey` codes in the lightcurve/alerts — **1 = ZTF detection, 2 = ZTF upper limit, 4 = LSST detection** (verified 2026-09-27; 2 is *not* LSST). LSST detections carry `ant_mag` plus ~140 `lsst_diaSource_*` / `lsst_diaObject_*` fields, incl. `lsst_diaSource_ssObjectId` (Rubin's own SSO association, 0 = none), `_reliability`, `_snr`, and `lsst_diaObject_validityStartMjdTai`.
- ANTARES: LSST alerts attach to existing loci within ~1", so most LSST detections sit on **old ZTF loci** (`ANT2018…`–`ANT2021…`, oldest alert years ago). A query on `properties.oldest_alert_observation_time` therefore never selects them; 0 of 400 new (< 14 d) loci carried an LSST ID. The `properties.survey.lsst.dia_object_id` array is not usable in an ES `exists` filter (returns nothing); the Rubin tags (`young_rubin_transients`, `lsst_scimma_quality_transient`) are the working server-side handle.
- LSST `query_lightcurve` returns **three** keys — `detections`, `non_detections`, `forced_photometry` — against ZTF's two. `non_detections` comes back empty even for well-sampled objects: Rubin publishes forced photometry where ZTF publishes upper limits. Detections carry fluxes (`psfFlux` nJy, convert with `reporting._psfflux_to_mag`) and `band`/`band_name`, never `magpsf`/`fid`.
- LSST forced photometry (ALeRCE `query_forced_photometry` / `query_lightcurve`) **starts at or after the first detection**: 16 of 16 objects checked 2026-09-27 had 0 forced epochs before it (first forced epoch 0–7 d after), and several stop at exactly 10 epochs. ANTARES serves no LSST forced photometry or non-detections at all (lightcurve codes 1/2/4 only). So neither broker currently provides pre-onset LSST photometry, and an LSST onset cannot be bracketed from broker data.
- CLI confirms before long runs: `_confirm_long_run` prompts y/N when the estimate exceeds `CONFIRM_THRESHOLD_SECONDS` (900s). **Only on a TTY** — under systemd there is no stdin, so it logs the estimate to stderr and proceeds rather than hanging the unit. `-y/--yes` skips it.
- ANTARES: `locus.alerts` includes both `ztf_candidate` (real detections, have `ant_mag`) and `ztf_upper_limit` (non-detections, no `ant_mag`). Pipeline filters to `ant_mag.notna()` before building the lightcurve.
- ANTARES: `locus.tags` returns plain strings (not objects); `locus.properties` contains num_mag_values which is the quality-filtered detection count.
